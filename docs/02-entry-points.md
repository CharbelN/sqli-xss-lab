# 02 — Entry-Point Inventory

Generated by `scripts/crawl_entrypoints.py` (scoped to `testaspnet.vulnweb.com`).
Raw data: [`evidence/crawl/entrypoints.json`](../evidence/crawl/entrypoints.json).

The crawler walked 16 pages (depth 2) and found **3 URL-parameter entry points**
and **14 form instances** (several are the same form on different pages). These
are the places user input enters the application — the attack surface for SQLi/XSS.

## URL-parameter entry points (GET)

| # | Method | Path | Parameter | Example | Why interesting |
|---|--------|------|-----------|---------|-----------------|
| 1 | GET | `/Comments.aspx` | `id` | `id=1` | **Assigned target.** Numeric row selector → classic SQLi candidate. |
| 2 | GET | `/ReadNews.aspx` | `id` | `id=0` | Numeric row selector → SQLi candidate. |
| 3 | GET | `/ReadNews.aspx` | `NewsAd` | `ads/def.html` | Path-like value → path/parameter handling, secondary candidate. |

## Form entry points (POST)

| Form (action) | Notable user fields | Why interesting |
|---------------|--------------------|-----------------|
| `/Comments.aspx` | **`tbComment`**, `btnSend` | **Stored-XSS candidate** — free-text comment rendered back on the page. |
| `/login.aspx` | `tbUsername`, `tbPassword`, `cbPersistCookie` | Auth form → SQLi-in-login candidate. |
| `/Signup.aspx` | `tbUsername`, `tbPassword` | Registration → SQLi / stored-input candidate. |
| `/default.aspx`, `/about.aspx` | (only ASP.NET state fields) | No user-controlled fields; low priority. |

Every ASP.NET form also carries `__VIEWSTATE`, `__VIEWSTATEGENERATOR`, and
`__EVENTVALIDATION` hidden fields. These are **not** user input, but they must be
replayed on POST or the server rejects the request — which is why the stored-XSS
probe harvests them before submitting (`scripts/xss_stored_probe.py`).

## Prioritization for this lab

Given the assignment (SQLi + XSS), testing focused on:

1. `/Comments.aspx?id=` — SQL injection (assigned) **and** the `tbComment` field for stored XSS (same page).
2. `/ReadNews.aspx?id=` — second SQL-injection candidate.
3. URL-parameter reflection on `/ReadNews.aspx` — reflected-XSS check.

A key early observation that shaped the XSS testing: **ASP.NET Request Validation**
is active for query strings on this app. Injecting `<` into a GET parameter returns
an error page —

```
A potentially dangerous Request.QueryString value was detected from the client (id="<...>").
```

— so the *reflected* XSS vector via URL parameters is mitigated by the framework.
The *stored* vector via the comment POST body is **not** mitigated (see
[`03-phase1-manual.md`](03-phase1-manual.md)), which is the realistic, interesting result.
